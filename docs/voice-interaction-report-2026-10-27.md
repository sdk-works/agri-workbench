## 2. 本轮改了什么

### 2.1 模型路由（提交 `603826c`）

`useFast` 加 `&& !voice`。语音一律留在强角色，不再覆盖模型名；文字短问行为不变。

这条改动**在当前配置下看不出任何差异**（fast 与 local 同款），价值在于关掉了一个随时会咬人的机制：哪天把 fast 换成小模型，语音就会集体降级。

顺带修了 `policy.test.mjs` 里一个早就失配的断言——`imageRole` 在"两个首选都不可用"时要退回候选池第一个能看图的角色，参照实现还停在无条件 `"local"`，等价性测试因此**一直是红的**。

### 2.2 语音交互（提交 `96af245`）

| 问题 | 改法 |
|---|---|
| 只有上传有超时，识别/生成卡住就永远转圈 | 识别 20s、首字 35s、合成 30s；首字超时用独立标志区分"模型没响应"和"用户主动打断" |
| 点了暂停还显示"直接说话" | 补 `failed` 态和暂停态独立文案 |
| 连续模式没人说话时永远停在"我在听" | 15 秒无有效发声自动暂停并说明 |
| 断网后"失败→自动重听→再失败"死循环 | 连续两次识别失败就停下，等人处理 |
| 播报期间不能开口打断 | 见 2.3 |
| 说不清慢在哪一段 | 见 2.4 |

### 2.3 开口打断（barge-in）

要在 AI 说话时听用户，就必须在播报期间开着麦，于是有"自己打断自己"的风险。三道防线：

1. 前 700ms 是保护期，**只采样不判定**，把扬声器泄漏的底噪记成基线
2. 阈值取 `max(0.05, 基线 × 2.5)`，跟着设备的回声消除效果自动调整
3. 必须**连续 320ms** 超阈值才算人声——咳嗽、碰麦、单帧噪声都不触发

> **风险声明**：这条只用假麦克风验证过"不会崩"，**没有在真实扬声器下验证会不会误触发**。iOS Safari 的 AEC 在 Web Audio 与 HTMLAudio 混用时表现不稳定，真机上最可能出现"AI 把自己打断"。若发生，可在 `localStorage` 置 `voice.bargein = 0` 关闭。

### 2.4 分阶段埋点

- SSE 每个事件带 `elapsed_ms`，`done` 带 `first_delta_ms / total_ms / role`
- 前端再记 ASR 耗时与"第一段声音真正播出来"的时刻，每轮收尾打一行日志
- 服务端把 `first_delta_ms / total_ms / role / 实际模型名` 落进 `turns.timing`

落库时模型名按角色从当前配置解析，不信任前端传值。这样事后能回答"是没收到图、没进视觉模型，还是模型本身慢"。

## 3. 分阶段耗时（隔离栈，中位数，**模型已预热**）

统计方式：先跑 2 轮热身让模型进显存，再跑 3 轮取中位数。

| 阶段 | 耗时 | 说明 |
|---|---|---|
| ① 识别（ASR） | **1201 ms** | 三轮 1314 / 1193 / 1201 |
| ② 模型首字 | **747 ms** | 三轮 869 / 278 / 747 |
| ③ 首段可听声音 | **2490 ms** | = 首句生成 1107 + 该句合成 1383 |
| ④ 完整回答 | **3290 ms** | 三轮 3290 / 2229 / 4512 |
| 带图 · 首字 | **615 ms** | 两轮 615 / 284 |
| 带图 · 完整 | **1968 ms** | 两轮 1968 / 1149 |

**结论：瓶颈在 TTS 合成，不在模型。** 首句 1107ms 就生成好了，但要再等 1383ms 才合成完，用户才能听到——首段可听因此被推到 2.49s。

想接近 ChatGPT 的响应感，最有效的一步是**流式 TTS 或预合成首句**，而不是换模型。按当前数据，把 TTS 首包压到 300ms，首段可听就能从 2490 降到 1400 左右。

> 这几个数是单用户、无并发、模型常驻显存的情况下测的。多人同时用会明显变长，尤其显存吃紧时。

## 6. 视频功能（本轮不做，先给方案）

**限制（建议值，需按实测调整）**

| 项 | 建议 | 理由 |
|---|---|---|
| 大小 | ≤ 60 MB | 手机流量与上传超时（当前上传超时 45s） |
| 时长 | ≤ 60 s | 与单次语音上限一致，避免用户以为能录一集 |
| 格式 | mp4 / mov / webm（H.264/AAC 优先） | iOS 与安卓都能直接解码 |
| 分辨率 | ≤ 1080p | 更高对叶片诊断没有增益，只是变慢 |

**处理流程**

1. 前端用 `<video>` + canvas 抽帧，**不做转码**（手机端转码又慢又费电）
2. 抽帧策略：前 3 秒每秒 1 帧，之后每 2 秒 1 帧，最多 12 帧
3. 每帧压缩到长边 1280、JPEG 0.85，带 `t=秒数` 元数据
4. 帧作为一组附件随轮次提交，服务端按顺序喂给视觉模型
5. 回答里引用时间点（"第 8 秒出现的斑点"），让用户能对回去

**必须诚实标注的地方**

- 只分析抽出来的图片，**中间过程没看到**。界面上要写明"已分析 12 帧（每 2 秒 1 帧）"，不能写成"看完了整段视频"
- 抽帧会漏掉帧间的短时事件（比如 0.5 秒的虫子在爬），这个局限要告诉用户
- 音频（风声、机器声、人说话）本轮**不处理**。若要处理需单独接 ASR，和视觉结果合并——那是另一个工作量

**为什么单独一包**：抽帧、时间轴对齐、多帧合成的提示词、帧级引用，每一项都要独立验证。塞进这轮会让"语音+图片"这个已经跑通的闭环变得不可回归。
